## 2026-07-06 — FEATURE-107: Decouple login-notification recognition from the history-write race + shared fingerprint helper (review C14)

Closed C14: LoginNotificationListener (priority 10) and LoginHistoryListener (priority 0) both fired on LoginSuccessEvent and both recomputed hash('sha256', ip.ua) verbatim; the notifier's "is this device known?" check queried login_history — the SAME table the history listener writes into — so alerts only worked because the notifier happened to run first. Reordering the listeners would make the current login match its own freshly-inserted row (every device "known" => alerts silently stop, no error, no failing test), and any drift in the duplicated formula meant "new device on every login". Root cause: one value (the login_history fingerprint) was overloaded for two jobs (history record AND recognition memory), coupling the listeners via run-order.

### What was built
- NEW src/Security/LoginFingerprint.php — the fingerprint formula (sha256(ip.ua)) and request-context extraction (ip default 0.0.0.0, UA substr 0..512) defined in ONE place; both listeners call it so it can no longer drift (AC1, AC8).
- NEW src/Entity/LoginNotificationSeen.php + src/Repository/LoginNotificationSeenRepository.php — dedicated marker store login_notification_seen (user_id + marker VARCHAR(64), UNIQUE(user_id, marker)); hasSeen()/markSeen() (persist+flush, swallow UniqueConstraintViolationException per ADR-030). LoginNotificationListener computes marker = mode === 'ip_only' ? ip : fingerprint, sends iff no seen-row, then records it — recognition NEVER reads login_history, so listener order is irrelevant (AC2), first-new-device notifies / repeat does not (AC3), recognition_mode honoured (AC4).

Date: 2026-07-06 | priority should | depends_on FEATURE-110 (satisfied) | passes:false->true

### Problem
A soft-deleted/deactivated account is barred from login (UserChecker/AdminChecker), but its
outstanding recovery artefacts stayed live: password_reset_tokens / admin_password_reset_tokens /
magic_link_tokens rows remained unused+valid, and the reset controllers reloaded the account by
email without ever checking its status — a live reset link in an old inbox (or an admin-triggered
reset) could still set a fresh password on an inert account.

### Change
- NEW src/Security/RecoveryTokenInvalidator.php — autowired service; invalidateForUser($email)
  bulk-marks PasswordResetToken + MagicLinkToken rows used, invalidateForAdmin($email) does the
  same for AdminPasswordResetToken (bulk DQL UPDATE usedAt=now WHERE email=:e AND usedAt IS NULL,
  mirrors the existing invalidateOtherUnusedTokens pattern; idempotent).
- Invalidator called at EVERY account->inactive transition (driven by the action, not row removal):
  AdminUserController edit(status=inactive)+delete; Api/AdminApiUserController update+delete+
  deactivate; AdminAdminManagementController edit(status=inactive)+delete. Create paths excluded
  (a new account has no outstanding tokens).
- Consumption gate (defence in depth, GET+POST, before any password mutation):
  PasswordResetController::reset + AdminPasswordResetController::reset reject when the token's
  account is null or not active — render reset template with token=null + "no longer valid".

### Tests
- NEW tests/Functional/Security/RecoveryTokenInvalidationTest.php (7 tests / 18 assertions):
  deactivate + soft-delete invalidate reset/magic-link tokens for user and admin; consumption
  rejected for inactive user and admin with the password hash unchanged. Each genuinely fails on
  pre-fix code (token stays unused / reset succeeds).

SafeRedirect.php::localPathOr(); TwoFactorChallengeListener stores getRequestUri()
(local path) and TwoFactorController re-validates it — post-2FA redirect is same-origin
by construction. No schema change, no migration, no new config key.

Admin "Remember Me" (ADR-051). Ken asked for a remember-me on /admin/login that (1) prefills the email
on next load and (2) keeps an admin signed in for 21 days, pushed back on every hit of activity; he
also called PHP's 24-minute session default "too onerous (it's like a bank website)" and asked for a
3-hour baseline driven from the DB.

Implemented by EXTENDING THE SESSION rather than enabling Symfony's remember_me on the admin firewall.
ADR-049's CRITICAL PRECONDITION says an admin remember-me bearer cookie reopens review finding C3
(revoked access surviving a cookie) unless an Admin::sessionsInvalidatedAt marker is added and bound
into the cookie HMAC. A long session sidesteps that entirely: terminate-all / soft-delete / deactivate
delete the admin_sessions row and AdminSessionRequestListener deauths on the next request, so the
session route is strictly safer, needs no new Admin column and no migration, and leaves the ADR-049
precondition satisfied (admin firewall still has NO remember_me). It also resolved the open 2FA
question for free — _admin_2fa_verified is session-scoped, so a remembered admin is not re-challenged
for TOTP inside the window, and no admin trusted-device mirror was needed.

Mechanism: Symfony has no per-firewall session config, but PdoSessionHandler takes a `ttl` CLOSURE
evaluated on every write AND on updateTimestamp — so ConfigAwarePdoSessionHandler (a subclass; a
closure can't be expressed in YAML args) supplies one backed by SessionTtlResolver, which reads
session.idle_lifetime_minutes (default 180) or session.remember_me_lifetime_days (default 21) when the
session carries the checkbox flag. Because sess_lifetime is re-stamped every request, the window
slides on activity with no refresh listener of our own. The resolver memoises per request (one config
query, not one per write) and never throws — it falls back to the baseline rather than breaking
session writes. cookie_lifetime raised to 21d as a browser-side hint only; server TTL is
authoritative, and raising the DB value past 21d requires raising cookie_lifetime too (noted inline).

Email prefill is separate and opt-in: last_username is session-scoped so it cannot survive an expired
session; ticking the box writes a long-lived HttpOnly ADMIN_LAST_EMAIL cookie (email only) which
AdminSecurityController uses as the last_username fallback and to re-tick the box. Explicit logout
clears it; mere session expiry does not (that's the case prefill exists for).

Gotcha worth remembering: services_dev.yaml and services_acceptance.yaml declare NO _defaults, so
autowiring is OFF in those files — the first verify run had 92/96 acceptance failures from
"Argument #2 ($ttlResolver) not passed". Wired explicitly there.

Tests: SessionTtlResolverTest (6, resolution rules incl. zero/negative flooring, no-request and
unstarted-session fallbacks, memoisation), ConfigAwarePdoSessionHandlerTest (3, writes a real SQLite
session and asserts the absolute sess_lifetime expiry — proves the TTL reaches the row),
AdminRememberMeTest (6 functional, incl. terminate-still-wins), AdminRememberMeCest (3 acceptance,
exercising the REAL handler the functional suite's mock storage can't).

## Added the standard SQLite connection baseline (ADR-056)

## FEATURE-150: Htaccess Lock (ADR-059)

Ken: internal tools should not be wide open; wants a web-server-level IP-whitelist lock edited from the
admin panel. Standard env is LiteSpeed/.htaccess (so my Caddy-vs-Apache worry was moot for their prod).
Decided mid-build: TECH-SUPPORT ONLY (not even superadmin); nav link "Htaccess Lock" under Maintainer.

Built: src/Htaccess/* (validator = injection boundary; renderer; HtaccessFile editing only a marked block,
prepended, atomic, serialised; manager over the config store; loopback self-test), controller + page,
app:htaccess-lock:disable console recovery, sidebar link, docs/htaccess-lock.md.

Key finding — verified on a REAL Apache 2.4 (apt-installed in the sandbox) instead of assuming: a plain
`Require` denial is always 403. A real 404 needs an `ErrorDocument 403 <local path>` internal redirect plus a
rewrite on REDIRECT_STATUS=403 -> R=404. Things that did NOT work (kept me from shipping them): rewrite with
no ErrorDocument 403 path (never fires), `<If>`-scoped ErrorDocument 404 (broke the remap), `ErrorDocument
403 " "` text (no redirect, so no remap). Final four shapes (403/404 x file/blank) all tested with curl.

The self-test is the important safety feature: a .htaccess lock fails OPEN if the server ignores it. It
requests the site over loopback (CURLOPT_RESOLVE -> 127.0.0.1) so the server sees a known source IP, checks
blocked / exempt / own-IP-inserted / configured-status, then restores the original file in `finally`.
Lockout protections: validator refuses to enable unless the admin's own IP is whitelisted; console disable.

Caught by tests: a literal `%` inside a sprintf error message (only on the rejection path) blew up with
ArgumentCountError; fixed. Mutation-checked the tech-support gate and the lockout guard. A test helper
originally overwrote the saved whitelist when toggling Off (test bug, not product) — fixed.

NOT verified: LiteSpeed itself (no LiteSpeed here). Run the in-app self-test once on each real host.
PHPUnit cannot prove enforcement (PHP built-in server has no .htaccess) — tests pin text + logic only.

verify-fast green (882 PHPUnit / 2789 assertions; 106 acceptance / 373).
